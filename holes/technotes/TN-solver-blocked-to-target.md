# Solver-blocked to ConstructionTarget and requeue: discovery

Date: 2026-08-26.  Code examined at futon3c `da717ab03e5cc0751c4d880696e703fef1995b1a`; apm-lean working repository was searched across 222 refs and all registered worktrees.

## 1. What happens after Solver exhaustion

The live Solver budget is 50 rounds (`src/futon3c/apm/live_solver_rounds.clj:11`). An invalid terminal turn is appended to `:rounds`; below the budget the controller dispatches another round (`live_solver_rounds.clj:371-375,393-436`). At the budget it persists `:state/type :solver-human-intervention-required` and returns the same error code (`live_solver_rounds.clj:424-431`). A repeated identical validator failure and an invalid strategy checkpoint stop earlier for remediation rather than consuming the proof-search budget (`live_solver_rounds.clj:377-413`); a Solver claim of a defect stops for defect review (`live_solver_rounds.clj:415-422`). Only a validated solution becomes `:live-job-certified` (`live_solver_rounds.clj:357-370`).

The queue adapter sees exactly `:solver-human-intervention-required` at the `set-alight!` call site and converts it to a frame park (`src/futon3c/apm/countdown_control.clj:1664-1692`). The park preserves the final head, branch, state path, last valid receipt and last failure-account item, marks `:student/decision :claude-required`, and explicitly does not decide whether Student should run (`src/futon3c/apm/queued_frame_adapter.clj:26-56`). Thus no automatic Student/Zai handoff follows exhausted Solver. Retry is an ordinary Solver round below the cap; at the cap the machine parks for a Claude decision.

`problem-queue-supervisor/tick!` validates that park, appends it to `:parked`, clears the active frame, persists, and prepares the next item from the queue plan (`src/futon3c/apm/problem_queue_supervisor.clj:223-279`). This is the actual automatic path: park this frame, then advance the queue.

`:library-infrastructure-absent` is not produced by source code. An `rg -n "library-infrastructure-absent" src test holes` search found it only in the hand-authored decision ledger (apart from prose referring to that ledger), not in `src/` or `test/`. The f43 row names `:decision/by "claude-12"` and assigns that class (`holes/labs/M-apm-demonstration/frame-park-decisions.edn:228-240`); its mathematical audit and rationale are likewise fields in that decision (`frame-park-decisions.edn:242-293`).

`futon3c.apm.frame-park-decisions` is a command-line reconciliation tool, not an automatic classifier. `reconcile-files!` reads a decisions file and queue-state file and rewrites queue state when a match changes it; `-main` merely invokes that function (`src/futon3c/apm/frame_park_decisions.clj:22-34`). The underlying reconciliation matches the last valid receipt and attaches the record, but its docstring is explicit that the disposition is “recorded but never executed” (`src/futon3c/apm/problem_queue_supervisor.clj:94-132`). The f43 decision itself says it was applied through this tool rather than by hand-editing queue state (`frame-park-decisions.edn:294-299`).

## 2. How a ConstructionTarget is created today

There are two related but separate systems. The files-only Library Loop is manually initialized with a problem id, an existing absolute apm-lean worktree, base SHA and initial head (`README-library-loop.md:20-30`; `src/futon3c/apm/library_loop_exec.clj:408-432`). Its durable state starts with those values and phase `:turn-ready` (`src/futon3c/apm/library_loop_runner.clj:51-69`). It is not invoked by the frame-park path above.

Within that worktree, the constructor creates or changes `ConstructionTargets/<Module>.lean`. Registration also requires the problem-local `problems/<pid>/targets.edn`; every row has a unique module, positive `:created-turn`, keyword status and nonblank obligation (`src/futon3c/apm/library_loop_targets.clj:53-69`). Production additionally requires a nonempty `:declarations` vector because the audit builds the module and runs `#print axioms` on each declaration (`src/futon3c/apm/library_loop_tools.clj:73-115`; `README-library-loop.md:68-89`). A new module must have a nonempty sibling `.md` seam document, exactly one disposition (imported by `ConstructionTargets.lean` or listed in `ConstructionTargets/PARTIAL.md`), and a ledger row (`src/futon3c/apm/library_loop_targets.clj:139-170`). Delayed registration also needs provenance proving the first-add commit and creation turn (`library_loop_targets.clj:171-183`; `README-library-loop.md:91-99`).

There is no independent “target slate” API accepting a theorem statement. `library-loop-slate` is only the demonstrator success scoreboard (`src/futon3c/apm/library_loop_slate.clj:1-34`), and the executable's `init` accepts a worktree and SHAs, not a proposed target (`src/futon3c/apm/library_loop_exec.clj:408-420`). Consequently the minimal current intake is a prepared problem worktree/run plus repository edits: Lean module, seam doc, disposition, and `targets.edn` record—not a queue row containing a statement.

An unproved target can exist during construction, and the `:status :active` ledger shape documents that working state (`README-library-loop.md:68-77`). It cannot pass the green registration/banking gate with `sorryAx`: each changed module requires a successful head-bound axiom audit (`src/futon3c/apm/library_loop_targets.clj:124-150`), and the production audit explicitly rejects failed builds, unknown declarations, failed audit elaboration, or `sorryAx` (`README-library-loop.md:79-89`). Thus “slating” an unproved theorem presently means starting a Library Loop worktree with an active target edit; it does not mean landing that target on trunk.

## 3. Requeue-at-end and inherited artifacts

There is no append-to-end operation for the active queue. A queue plan is content-addressed over a fixed vector of pinned problem fields (`src/futon3c/apm/problem_queue_supervisor.clj:47-53`), rejects duplicate problem ids (`problem_queue_supervisor.clj:55-73`), and `prepare-next` consumes it by numeric cursor (`problem_queue_supervisor.clj:190-221`). Searches for queue append/requeue APIs found only the same-problem rollover below.

That rollover does preserve an inherited artifact. `retry-problem` replaces the problem's base branch, revision and blob with the retained Solver branch/head/blob (`src/futon3c/apm/solver_progress_rollover.clj:55-60`). Its caller resolves the problem file's blob at the Solver final head and returns the rewritten problem pin (`src/futon3c/apm/countdown_control.clj:1893-1908`). But this path applies only to a specially certified round-10 partial checkpoint: `derive-terminal` requires ten rounds, a committed clean head, successful Lean with positive sorry warnings, and matching workspace heads (`solver_progress_rollover.clj:8-53`). It then calls `complete-active-without-successor`, whose contract deliberately leaves the cursor unchanged and requires callers to disable this queue before starting a *distinct* same-problem retry queue (`problem_queue_supervisor.clj:162-188`). It is precedent for artifact inheritance, not for placing an item at the back of the current queue.

For a97J08, requeueing the pristine corpus pin would discard the point of the operation. The retained problem pin must use the final artifact head/blob in the same way as `retry-problem`; whether a 1962-line inherited base remains comparable with the original experimental arm is a measurement decision for Joe, not an implementation detail.

## 4. Recommended seam

The honest smallest design is a new, typed post-Solver obstruction-triage transition, not a hook that silently turns every exhausted park into a target. Its observation seam is the existing exhaustion branch immediately before `solver-human-intervention-park` (`src/futon3c/apm/countdown_control.clj:1681-1692`), because that is where the final head/state and residual are still together. The triage output should contain at least the exact theorem declaration/statement, source problem, Solver final head and problem blob, proposed ConstructionTarget module/obligation, and a decision class. It should be receipt-bound and independently reviewed; the current park only contains an opaque residual string and has no typed theorem statement (`src/futon3c/apm/queued_frame_adapter.clj:31-48`).

The effect seam belongs after an authoritative decision, not inside `reconcile-park-decisions`: that function promises only to attach records and never execute them (`src/futon3c/apm/problem_queue_supervisor.clj:94-132`). A new queue-supervisor transition should atomically (a) create a Library Loop intake/run from the retained worktree/head and typed target proposal and (b) construct a new content-addressed successor queue whose last item is `retry-problem`'s retained revision/blob. The present plan cannot be mutated consistently because its digest covers the problem vector and duplicate ids are forbidden (`problem_queue_supervisor.clj:47-73`). This likely warrants an explicit successor-queue phase/receipt rather than modifying `tick!`'s existing park-and-advance branch.

I would **not** send the obstruction to Student/Zai: no code presently makes that transition, and an absent library theorem is not a student-memory test. I would not create a ConstructionTarget from prose without an exact Lean statement, duplicate search and independent review. I would not put a sorry-bearing target on trunk, bypass the axiom gate, mutate a content-addressed queue plan, or requeue the pristine problem while losing the Solver artifact. Finally, I would not treat results from an inherited 1962-line base as the same experimental condition without Joe explicitly approving that change.

## 5. Duplication risk

The exact f43 statement is present in the banked problem on apm-lean `origin/master`: the first theorem states the bounded-complement-component/noncontractible-circle obstruction and carries one sorry, followed by the explanatory comment (`problems/a97J08/lean/Main.lean:1796-1812` at `origin/master`); the subsequent theorem consumes it (`problems/a97J08/lean/Main.lean:1820-1823` at `origin/master`). The canonical apm-lean checkout was on another branch during this audit, so these citations deliberately name the inspected ref rather than its shorter working-tree version.

I searched the current 49 `ConstructionTargets/*.lean` files and their seam docs with case-insensitive patterns for bounded complement components, non-nullhomotopic circles, contraction in the domain, Jordan, winding and planar separation. The nearby modules are not duplicates: for example `EmbeddedCirclePreimage` packages **null** winding from component hypotheses (`/home/joe/code/apm-lean/ConstructionTargets/EmbeddedCirclePreimage.lean:24-30,65-74`), while `TransversePreimageDuality` packages a nonzero-top-map/non-null-winding implication (`/home/joe/code/apm-lean/ConstructionTargets/TransversePreimageDuality.lean:37-61`). Neither starts from a bounded component of a planar complement or produces a loop in the domain.

I also enumerated all 222 refs under `refs/heads`, `refs/remotes`, and `refs/apm/` (using the `refs/apm/` prefix, not a non-recursive glob), deduplicated their head commits, and ran `git grep` over `ConstructionTargets/*` at every head for `bounded component of the complement`, `non.?nullhomotopic circle`, `cannot be contracted while remaining`, and `planar obstruction`. There were no matches. I enumerated every registered worktree with `git worktree list --porcelain`; the only exact statement found is the f43 problem artifact, not a ConstructionTarget. On the evidence visible in Git and registered worktrees, no in-flight target already states this obstruction. This cannot exclude uncommitted content outside registered worktrees or work communicated only in an agent conversation; the machine has no target-proposal registry to query, which is itself part of the duplication risk.
