# GCC use cases as real XTQL against live futon1b (kimi-1, 2026-11-12)

Follow-up to `GCC-use-cases-2026-11-12.md` (c93c00d84), at claude-13's
requisition: write real XTQL for each of the 16 use cases against the live
futon1b store (:7073, queried in-JVM via Drawbridge :6769,
`futon1b-xt/timed-q`, deadline ≤ 10 s, limit ≤ 200, all values via `pq`
parameters), and list what is missing. No turn text or memory bodies are
quoted — ids and shapes only.

## 0. Mechanics learned (these shape every query below)

- **`pq` + `timed-q` work as documented**; all timings below are server-side
  (measured in the eval form) unless marked ~.
- **A `where` column absent from the `from` projection is unbound and the
  predicate silently matches nothing** (documented at
  futon1b `futon1b_evidence.clj:390`; I rediscovered it the hard way — my
  first six parameterised queries returned silent zeros for this reason).
  Every `where` column must appear in the projection.
- **Keyword parameters do not match keyword columns through the JDBC
  envelope; string parameters do** (coerced). `(= evidence/type ?)` with
  `:coordination` → 0 rows; with `"coordination"` → rows. Inline keyword
  literals also work. Use string params or inline keywords.
- **`>=` on the string column `evidence/at` works parameterised**
  (lexicographic — the production contract's own semantics,
  `futon1b_evidence.clj:407`). A parameterised `=` on `evidence/at` matched
  nothing in my hands while the inline literal matched; use range predicates
  for time, point lookups only on `xt/id`.
- **Nested destructuring in `from` (`{:evidence/origin {:kind k}}`) fails**
  (query rejected). Nested predicates (`body.event`, `origin.kind`) must
  post-filter in Clojure — which is exactly what the production evidence
  route and `turn_frames.py` already do.
- **Full-table aggregates on `:entities` and `:evidence`, and grouped
  aggregates on `:relations`, exceed the 10 s deadline** and surface,
  confusingly, as `CompilerException: Syntax error macroexpanding` after
  ~10 s (the JDBC deadline error, mislabelled). A timeout is a finding, not
  a syntax bug.
- **As-of syntax**: `(from :table {:for-system-time (at t) :bind [cols]})`
  with an `Instant` parameter (from `futon1b_evidence.clj:240-249`;
  `(as-of t)` is not the form).
- **minus40 (:7093) exposes no XTQL.** It is an HTTP JSON service; 狗's
  recall reads it as `GET /api/alpha/evidence/text-search?q=...`
  (`futon3c src/futon3c/agency/dog_provider.clj:11-20,62-64`). Its memories
  are not queryable from futon1b's node at all.

Operator turns are **evidence**, not entities, in the live system:
`evidence/type :coordination`, `body.event "chat-turn"`, `body.role "user"`,
`origin.kind :operator` (`turn_frames.py:508-518`). The `:operator-turn`
entities that exist are from an older bridge (`entity/source
"hinge-log-bridge"`, 2026-04) — a different id space from evidence ids.

Sessions: no `:session` rows found in the tables probed; sessions are
`evidence/session-id` strings. Patterns: `:entities` with
`entity/type :pattern`, `:pattern/component`, `:pattern/clause`. Missions:
`entity/type :mission`. Questions: `entity/type :question` (exist below).
Memories: **not in XTDB** — minus40 :7093 (HTTP JSON only); their presence
in the graph is via `:memory/assert` hyperedges (exist below).

## 2. The 16 use cases as XTQL

Timings are one sample each, server-side. "—" = cannot run today; the
missing piece is listed.

### UC1 — GCC projector incremental write + full-rebuild equality
**Cannot run.** There is no GCC record population to project: no
`[:pattern/occurrence]`, `[:situation/element]`, `[:cascade/reading]` rows
anywhere (the schema-1.1 types have no writer), and the turn records the
projector would read are files on disk
(`~/.emacs-graph/session-turn-analysis/`), not XTDB tables. Also relevant:
the equality check is a whole-graph aggregate, and whole-table aggregates
already exceed 10 s on `:entities` — the projector's check wants a derived
store, not ad-hoc XTQL.
*Missing: occurrence/element/reading tables (new derived); turn lifecycle
state in a queryable store (new derived).*

### UC2 — 猴: locate a settled turn's cascade
**Cannot run** (needs UC1's records). What the gluing part would look like
once occurrences and elements exist, against `:relations`-style storage:

```clojure
;; occurrences sharing an element with a given occurrence (sketch)
[(fn [o1] (-> (from :occurrence-elements [occ element])
              (where (= occ o1)))) o1-id]           ; its elements, then the
                                                    ; reverse lookup by element
```

*Missing: occurrence and element records (new derived); the connected
component itself is graph reachability XTQL does not do — computed in
Clojure over the edge rows.*

### UC3 — Giraffe pass: readiness over `needs` edges
**Edges are absent.** `(from :relations … (where (= relation/type :needs)))`
→ 0 rows (fast — the type simply doesn't exist). Today's pass reads a run
file. Once `needs` edges are records, the per-edge fetch is the UC6 point
query; readiness/cones/cycles remain Clojure over the edge set, as
`giraffe/pass.clj` already works.
*Missing: `needs` edges as records (new derived; today in Giraffe run
files).*

### UC4 — Giraffe priority projection (band by 猴 focus)
**Focus input absent** (猴 has no writer). The projection itself is a per
-target point lookup — trivially served once focus relations exist:
`[(fn [t] (-> (from :focus-relations [target relation]) (where (= target t)) (limit 1))) target-id]`.
*Missing: 猴 focus records (new derived, schema 1.1).*

### UC5 — Coverage check
Partially runnable. The evidence side — operator turns in a window — works
(UC11 query below). The settled-records side does not: lifecycle state
(`:recorded`…`:settled`) lives in the turn-record files, not XTDB, and the
per-turn animal fields likewise. The set difference itself is cheap Clojure
once both sets are in hand; the windowed evidence scan is the only XTQL
part.
*Missing: turn lifecycle state and per-animal field presence as records or
columns (new derived); a queryable settled-turn index.*

### UC6 — CTRL: "is a linked to c?" (+ wants)
Runs today against `:relations` (48 ms server-side):

```clojure
[(fn [s ty d] (-> (from :relations [xt/id relation/src relation/type relation/dst])
                  (where (= relation/src s) (= relation/type ty) (= relation/dst d))
                  (limit 1)))
 "696f0808-…" :arxana/scholium "f19fbb66-…"]   ; => 1 row
```

Works identically against `:hyperedges` by `hx/type` + endpoint membership
(endpoint-in-vector needs unnest/post-filter; the `hx_*` SQLite sidecar
already indexes endpoints — see §4). "a links to c *eventually*" — the want
record with horizon — has no table (E-gcc-schema B7: **[open]**).
*Missing: want records (new derived); `[[X]]` introductions awaiting
referents are not on the live store either (B6 built on :7094 only).*

### UC7 — War Machine wants with locators (C3–C8, T1)
**Cannot run**: no want records, and the locators read git objects / the
test registry / conversation text — all outside XTDB. The observation
status write has no home.
*Missing: want records, locator class column, observation status (all new
derived).*

### UC8 — `[:cascade/aims-at 1]` joins
**Cannot run**: needs occurrences, elements and wants — all absent.
*Missing: as UC1/UC2/UC7.*

### UC9/UC10 — Mojira / Emacs cascade views
The cascade data (occurrences, elements, glue) is absent (UC1). What runs
today is the frame-level fetch behind them — the UC11 window query plus
per-id hydration. `cascade-reader.js` is "the one module to swap for a GCC
query later" (futon4 `dev/mojira/cascade-reader.js:4`).
*Missing: as UC1.*

### UC11 — 象 stepper: one session's frames
Runs today (537 ms for a 2-day window, limit 20, no order-by):

```clojure
[(fn [since] (-> (from :evidence [xt/id evidence/at evidence/type
                                  evidence/author evidence/session-id
                                  evidence/in-reply-to])
                 (where (= evidence/type :coordination)
                        (>= evidence/at since))
                 (limit 20)))
 "2026-11-10"]   ; => 20 rows, e.g. e-8d0a6ba3…, e-a2b5ca8f…, e-c25a26ad…
```

Caveats measured: `order-by {:evidence/at :desc}` over the window **exceeds
10 s** (the production route streams and top-K's in Clojure for this
reason); operator-turn discrimination (`origin.kind`, `body.event/role`)
must post-filter (nested predicates unsupported); per-id hydration should
use `_id = ?` point reads, never `IN` (`futon1b_evidence.clj:257-265`:
2,101 ms vs 17 ms).
*Missing: nothing structural — this is the store's strongest suit today.*

### UC12 — 狗 recall / bury
**Not against XTDB.** Memories live in minus40 (:7093), HTTP JSON only, no
XTQL surface. What XTDB holds is the graph trace of memories:
`:memory/assert` hyperedges linking evidence ids to problem/memory/agent
ids:

```clojure
[(fn [ty] (-> (from :hyperedges [xt/id hx/type hx/endpoints])
              (where (= hx/type ty)) (limit 2)))
 :memory/assert]
;; => hx-mem-cc07f1d6… endpoints ["e-cc07f1d6…" "a01J05" "124c6765…" "zai-8f8c4736…"]
```

A GCC answer to "which memories bear on this turn" via `[[links]]`
neighbourhoods would need memories as nodes — they are not ingested.
*Missing: memory nodes/edges (new derived, or federation to :7093 over
HTTP); the 100 ms Prompt-line budget rules out a two-hop HTTP+XTQL chain —
this is an argument for projection into whatever fast store is chosen.*

### UC13 — Following a 驴/狗 line item one ring out
Runs today for anything with an entity or relation presence:

```clojure
;; relations out of a node (fast, <1 s)
[(fn [s] (-> (from :relations [xt/id relation/type relation/dst relation/src])
             (where (= relation/src s)) (limit 5)))
 "696f0808-f158-40b9-94ca-0d9be83a7584"]   ; => 5 rows
```

and entity point lookup by `xt/id` (= on `xt/id` works parameterised).
Pattern → cascade hangs on UC1's missing records; memory → `[[links]]`
hangs on UC12.
*Missing: as UC1/UC12.*

### UC14 — Questions linked to turns and citations
Half present: `:question` entities exist (`1bc5e179-…`, `d59d00bc-…`).
The links question↔turn and question↔citation do not (no such relation
types observed; E-futon-questions item 5 proposes them).
*Missing: question↔turn/citation link records (new derived).*

### UC15 — War Machine reads Giraffe priorities
**Cannot run**: Giraffe's pass/projection outputs are run directories and
:7073 review entries, not a queryable priorities table; and its inputs
(needs edges, focus) are absent (UC3/UC4).
*Missing: the priorities projection as records (new derived — or recomputed
on read from needs+focus once those exist).*

### UC16 — As-of queries
Runs, with the production syntax:

```clojure
[(fn [t] (-> (from :type-catalog {:for-system-time (at t) :bind [xt/id]})
             (limit 3)))
 (java.time/Instant/parse "2026-11-01T00:00:00Z")]   ; => 3 rows, <1 s
```

Caveat from the contract (`futon1b_evidence.clj:847-849`): the public
writer sets neither axis, so XTDB validity starts at insertion, **not** at
`evidence/at` event time — valid-time as-of over evidence does not mean
"what happened by date D" unless ingest sets valid time.
*Missing: valid-time discipline at ingest (a write-side change, not a
record).*

## 3. The missing list (first draft of what the GCC adds on top of XTDB)

**New derived records (nothing to join to today):**
1. `[:pattern/occurrence]`, `[:situation/element]`, `[:cascade/reading]`
   (schema 1.1; no writer) — blocks UC1, 2, 8, 9, 10, 13.
2. `needs` edges as records (today: Giraffe run files) — blocks UC3, 15.
3. 猴 focus records (schema 1.1) — blocks UC4, 15.
4. Want records with locator class, horizon, observation status (B7 open)
   — blocks UC6-"eventually", 7, 8.
5. Turn lifecycle state + per-animal field presence as queryable records —
   blocks UC1 (projector input), 5.
6. Memory nodes with `[[links]]` edges (minus40 is a separate HTTP service)
   — blocks UC12, 13.
7. Question↔turn/citation links — blocks UC14.

**Joins XTDB could already do if an id were recorded:**
8. Operator-turn evidence ids ↔ any entity/record that references them:
   the old `:operator-turn` entities use a different id space
   (`hinge-log-bridge`); nothing in `:entities` keys on live `e-…` turn ids
   — one recorded id per turn would join the stepper's world to the graph.
9. Hyperedge endpoints ↔ entities: endpoints are bare strings; an
   entity-name↔`xt/id` resolver exists (`:entities.entity/name`) so the
   join is one lookup away, but nothing records it.
10. Valid-time set from `evidence/at` at ingest would make UC16's as-of
    mean event time.

**Not records — store capability gaps found by running the queries:**
11. No nested-map predicates in XTQL (origin/body): post-filter or add
    derived scalar columns (e.g. an `:operator-turn` flag on evidence).
12. No reachability/recursion in XTQL: components, cones, cascade gluing
    are computed in Clojure over fetched edges (fine at these sizes; the
    sidecar candidates exist precisely for this).
13. Whole-table aggregates exceed interactive deadlines on the big tables —
    coverage and rebuild-equality checks want a derived store or the
    existing sidecars (`hx_*`, entindex), not ad-hoc XTQL.
14. Keyword parameters don't match keyword columns through the JDBC
    envelope (use string params or inline keywords) — a footgun for every
    future GCC query author.

## 4. Latency vs the survey's budgets

| query | measured | budget | verdict |
|---|---|---|---|
| CTRL triple lookup (`:relations`, UC6) | 48 ms | Prompt-line | **fast enough** |
| entity point lookup by `xt/id` | <100 ms ~ | Prompt-line | fast enough |
| relations one-ring by src (UC13) | <1 s | Prompt-line | fast enough |
| evidence window, limit 20, no sort (UC11) | 537 ms | Prompt-line | **borderline** — meets it, but a sort over the same window does not |
| evidence window + `order-by at desc` | >10 s (deadline) | Prompt-line | **too slow** — production streams + top-K in Clojure instead |
| as-of on small table (UC16) | <1 s ~ | offline/occasional | fine |
| full-table count `:entities`, `:evidence`; grouped count `:relations` | >10 s (deadline) | offline (coverage, rebuild-equality) | **too slow even offline at 10 s** — needs the derived store |
| `:hyperedges` / `:relations` / `:type-catalog` full counts | <10 s | — | OK |

Net: the live store already serves the point-lookup and small-neighbourhood
cases (the survey's dominant shapes) inside their budgets, *for the data
that is actually in it*. What it cannot do — reachability, whole-graph
checks, nested predicates, minus40 federation — plus the seven missing
record kinds above, is exactly the GCC's add-list. The slowest query class
was the unindexed sorted window scan over `:evidence` (>10 s); the slowest
necessary one was the full-table aggregate (>10 s, both big tables).
