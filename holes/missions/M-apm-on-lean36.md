## Why

1. **Reuse.** The openai/math drop and the other external Lean material (Schoenflies,
   TauCeti local homology / Stokes / covers, Lean Pool surface classification) are on Lean
   4.32–4.36. At 4.29, apm-lean can only use them by backporting, one file at a time.
   On current Mathlib we could import them. t00J05's cell-normal-form leaf
   (Schoenflies plus collar) is the first problem waiting on this.
2. **Upkeep.** Each month on 4.29 makes the next bump larger.
3. **Learning.** Joe (11-04): a 29→36 port is worth doing for what it teaches about how
   Mathlib changes, even where it gains no closures directly.

## Tracks

### A. Port apm-lean (the main track)

A0. **Type-change table.** Add a hash of each constant's type to `DumpEnv.lean` (branch
    `bump-env`) and rerun it on the old and new trees. Joining that with the uses table
    gives, for every file, the used constants whose *statement* changed. That is the
    worklist for class (c). Small: one Codex job.
A1. **Mechanical pass.** Apply the rename table plus the deprecation map, which comes free
    from the `replacement` column of the dump (154 deprecated constants are named in our
    source). Expect few new compiles; the point is to remove the noise from first errors.
A2. **Shared adaptations, in dependency order.** Repair each group once, in a reusable
    ConstructionTargets module, then let the problems that import it recompile. Order the
    groups by how many files each one unblocks, so the widest goes first:
    - simp normal forms: 57 files;
    - local path-connectedness: 44;
    - calculus instances: 44;
    - Lp / ENNReal: 32;
    - singular homology / SSet redesign: 28 files. This is the riskiest group. t00A04's
      new chain-level work sits on it.
A3. **Per-file repairs.** Lemma seats, one file per seat, using the same blueprint
    discipline. The gate for each file is compile, `#print axioms`, and the registry
    fingerprint unchanged.
A4. **Switch.** master moves to the new toolchain only when the registered-problem count on
    the new tree is at least master's (currently 470 closed). Until then, closures continue
    on master and A3 replays them.

**Acceptance.** Every registered problem that is closed on master is closed on the new tree,
with an unchanged statement fingerprint, and both trees report the same axioms.

### B. A version-to-version translator (Joe and Rob's idea; separate, research)

Read the Lean and Mathlib git history and derive rewrites mechanically, instead of
collecting hand patches. Rob's multiversion-to-29 patch set is the comparison point; the
translator must not depend on it.

What the history provides, roughly from cheapest to most expensive to extract:
1. Deprecation attributes: old → new name and a `since` date. These are already in the
   dump; a table can be built for any pair of versions.
2. Statement changes: the type-hash diff from A0, per constant and per version pair.
3. Mathlib PR diffs that changed a statement together with its in-tree uses. Each such PR
   shows its own migration, i.e. how Mathlib's own call sites were fixed. Mining these
   gives candidate rewrites for our call sites.
4. Simp-set and instance changes. These change proof states without changing any name, and
   are the main cost in A. It is not yet known whether they can be extracted from the
   diffs. This step settles whether the translator is "straightforward" or not.

Evaluation: rerun A's measurement (files compiling on the new tree) after each extraction
level, against the bump corpus. That corpus is a fixed 302-file test set with a known
first error for each file.

### C. Logic Atlas / an MMT importer for Lean 4 (exploratory; possible upstream PR)

Michael Kohlhase's group built the MMT system, OMDoc, and the LATIN / Logic Atlas: logics
and libraries expressed in a meta-framework, with translations between them as morphisms.
Valeria's point is that Lean is one of several systems. A version change is a small case of
library translation, Lean 4.29-Mathlib to Lean 4.36-Mathlib. Track B's rewrites could be
written as MMT views instead of string patches.

**State (checked 2026-11-04, three web searches; not exhaustive).**
- No Lean 4 importer for MMT turned up. The KWARC paper "Experiences from Exporting Major
  Proof Assistant Libraries" (Kohlhase, Rabe et al., JAR 2021, arXiv 2005.03089) covers
  Coq, HOL Light, IMPS, Isabelle, Mizar and PVS, but not Lean.
- A Lean Zulip thread mentions earlier Lean 3 work through the export format, using
  trepplein.
- `leanprover/lean4export` is a plain-text declaration exporter for Lean 4. It does not
  target MMT.
- Still to do: look directly at the UniFormal GitHub org and ask the MMT developers.

**Why mfuton is well placed** (Joe 11-04: a PR would likely be welcome; Joe knows Michael).
EmitPython already loads Mathlib-scale environments from oleans and walks every elaborated
constant. That walk produced the 3.09M-row uses table. Emitting each constant's
declaration (name, kind, type, value or proof term, and module) as OMDoc/MMT is a new
backend on the same walk, not a new reader. The Isabelle importer is the model to follow
for the structure of a library export.

**Deliverables, in order.**
1. A reading note on the Isabelle importer's shape and on MMT's input formats, with a
   proposal for how Lean 4's theory (CIC with universes, quotients, and the kernel's
   inductive types) would be stated as an MMT/LF foundation.
2. A prototype export of one small Lean 4 module.
3. Mathlib at 4.29 and at 4.36, so that track B's statement diff can be read as an MMT
   view between the two.

Open: can the atlas represent elaboration-level changes (simp sets, instances), or only
declarations and types? If only declarations and types, C serves B levels 1–2, not 4.
C does not gate A.
