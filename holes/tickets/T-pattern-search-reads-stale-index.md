# T-pattern-search-reads-stale-index — 115 library patterns are invisible to pattern search

**Status:** OPEN (opened 2026-11-08 by claude-6 at Joe's request; found while
checking that the militant-pacifism patterns reached the store)

**Date:** 2026-11-08

**Way of working:** files-mirrored-in-graph ("What is on disk is in the
graph"), declared the same day; this ticket is its first known violation on
the retrieval side.

## What happens

`GET /api/alpha/patterns/search` (futon3c `transport/http.clj`,
`handle-patterns-search` → `search-patterns`, ~line 4205) reads
`~/code/futon3/resources/sigils/patterns-index.tsv` through
`load-patterns-tsv` and keeps it in a `defonce` atom (`!patterns-cache`, ~line
4182) that is never reset. Two separate staleness sources:

1. **The file is regenerated by hand only.** Last written 2026-09-29 05:38
   (`scripts/pattern_index.py` / `reembed_flexiarg_tfidf.py` in futon3 write
   it). On 2026-11-08 the library has 1546 `.flexiarg` files; 115 of their ids
   are absent from the TSV: task-selection 20, self-heal 14, institutions 13,
   creativity-commons 13, efficiency 12, ways-of-working 10,
   argument-coherence 10, militant-pacifism 6, others.
2. **The running JVM never re-reads it.** Even a regenerated file is not seen
   until the namespace is reloaded or the JVM restarts.

Meanwhile substrate-2 has the patterns: all six militant-pacifism ids resolve
at `GET :7073/api/alpha/entity/militant-pacifism%2F<name>` as
`:pattern/library`. So the graph is current and the search is not: the store
and the search disagree, and nothing reports it.

## Why it matters

Pattern retrieval is what turn prompts, Giraffe readings and agents use to
find patterns (the "pattern ~…" line on every REPL turn comes from a
retrieval path). A pattern added since 2026-09-29 cannot be retrieved there,
including the ways-of-working and creativity-commons patterns that Cascade
Live cites. (Whether the per-turn retrieval uses this same TSV is not yet
checked.)

## Close condition

Searching `GET /api/alpha/patterns/search?q=demonstrable%20harm%20reduction`
returns `militant-pacifism/demonstrable-harm-reduction`, and a pattern added
to the library after the fix appears in that search without a manual
regeneration or a JVM restart. Either the search reads substrate-2 (the
store already has the entities), or the index is rebuilt and the cache
invalidated whenever the library changes; which one is a design choice for
whoever builds it.

## Not in scope

The substrate-2 completeness probe for files-mirrored-in-graph (a separate
piece of work); re-embedding vectors for similarity search, unless the fix
needs it.
