## HEAD (one line)

agent-follow-mode attaches the operator to one agent across all of its
conversations. A WM viewer would attach the operator to one run across all
of its agents (wm-author, wm-reviewer, ...), and keep a lab notebook of each
run. It would also reconstruct where the run's time and tokens went, phase
by phase: a decompiler for WM runs, not only a viewer.

## What exists (checked 2026-11-07)

- `futon3c/emacs/wm-follow-mode.el` (codex-18, dispatched by claude-6,
  `2a36df896` and `f209bbbea`, 2026-11-05). `M-x wm-follow` opens a
  read-only `*wm-follow*` transcript of the current click. It builds the
  view from `GET /api/alpha/wm/click`, new bytes in
  `futon2/data/wm-full-loop-phases.edn.log`, `wm-full-loop` Agency jobs,
  and cost receipts from `futon2/data/wm-click-loop/ledger.jsonl`.
  Test: `futon3c/test/wm-follow-mode-test.el`.
  What it lacks for a notebook:
  - it keeps only the last 8 click sections and saves nothing;
  - it is arranged by click and phase, not by role;
  - it records what happened, not what the run set out to do or what it
    learned.
- **Unit of a run.** WM already treats one click as one run: each ledger
  `click-id` pairs with one `run-id`, and each run gets its own report card.
  So one notebook covers one click; views across runs cover a session of
  many clicks.

## Data sources for the decompiler

Example run: `2026-11-06-e51be3f7-5510-4ccb-9f04-c2eac3036ff3` (17.6 min,
outcome `:grounded-progress`).

- **Phases:** `futon2/data/wm-runs/<run-id>/report-card.{edn,md,html}`.
  Work and wall time, outcome and restarts for each phase (28 phases in
  the example; `:author-wait` 407 s, `:selected-target-reading` 149 s,
  `:selection` 61 s).
- **Seats:** the same report card totals tokens in and out per role, with
  the role's job ids (wm-reviewer: 351,031 in and 3,764 out over 2 jobs).
- **Jobs:** `GET /api/alpha/invoke/jobs/<job-id>` returns `usage`
  (`cost/input-tokens`, `cost/output-tokens`, `cost/cached-input-tokens`,
  `cost/reasoning-tokens`, `cost/calls`, `cost/model`, `cost/source`),
  `total-cost-usd`, and `events`: a timestamped list of `prompt`, `text`
  and `tool_use` entries. In one reviewer job, 33,600 of the 40,504 input
  tokens were cached.

## Gaps

1. **Phase to job.** The phase log carries no job ids. Jobs have to be
   assigned to phases by time window, or through the job lists on the
   report card's seat rows. That is a reconstruction, not a recorded link.
2. **Tokens during selection.** In the example run no Agency seat was
   dispatched during `:selection`. Either selection runs in the JVM
   without a model, or it makes model calls that nothing records. Not yet
   checked. If it is the second, the first step is to record those calls
   (WM code, so Codex builds it).
3. **Inside a job.** Usage is recorded per job, not per model call.
   `events` give order and text sizes, so any breakdown inside one job is
   an estimate unless the harness starts recording usage per call.

## Packets (sketch; none dispatched)

Small, one behaviour each, with a Claude review between them. Zai seats
for 1, 2 and 4; Codex for any change to WM itself.

1. **Extractor.** For a run id, write one table of phase → job → event,
   with time and tokens attached, into `data/wm-runs/<run-id>/`.
   Acceptance: on the example run, per-job token totals match the report
   card's seat totals. Every viewer reads this table; none parses the logs
   itself.
2. **Marimo notebook.** `marimo-zone/notebooks/wm-decompile.py`, beside
   `wm-closure.py`, served by `marimo-zone` (:2718). Pick a run; tokens by
   phase and role, cached versus fresh input, a timeline, drill-down into
   one job's events. Later, the same views across runs.
3. **Selection probe** (discovery only). Does `:selection` make model
   calls? Answer gap 2 before packet 1 is finished.
4. **Emacs notebook.** Extend wm-follow-mode, reading packet 1's table:
   persist each finished click to its run's notebook; group entries by
   role as well as phase; give each run a header (goal, selected policy,
   starting state) and a closing entry (outcome, cost, what changed),
   taken from the ledger and the phase log, nothing generated by a model.
   Then `M-x wm-notebook` to browse past runs.
